# TC19: HardwareHarness self-hosting (rebuild oracle machine code from the registry)

## Context

Sourced from `TCB.md` **T10 — HardwareHarness's hand-written machine code** (TCB priority 4-tie).
The x86 hardware fuzzer — the differential oracle that validates the entire x86-64 semantics
model against real silicon (`docs/VISION.md` §3.2's first bullet) — is itself built out of **~600
bytes across 94 raw `ByteArray.mk` literals**, hand-encoded rather than produced by the encoder it
exists to validate. TCB's sharpest phrasing: "the oracle validating the encoder is not built by
the encoder" — `mov r64, imm64` is hand-written at 14 separate sites even though `mov_r64_imm64`
already exists as a proper encoder function. `setupSize := 46` is a manually-asserted constant
that nothing checks against the actual hand-written byte count. `HardwareHarness.lean:270` calls
`emitPE32Executable` directly, which TCB flags as "a live counterexample to 'binaries only via
`emitVerifiedExecutable`'" — a legitimate one (the harness deliberately runs raw candidate machine
code as its whole reason for existing), but worth naming precisely so it isn't confused with an
accidental violation of `docs/REVIEW.md` §4.1 item 1's code-generation gating.

The harness's control-vector discipline is otherwise TCB's own reference example — the harness
that was "caught failing open twice" is the reason its positive/negative sanity checks
(`HardwareHarness.lean:331-336`, cited from TC5's file) exist at all, and TCB explicitly calls this
harness's three-control architecture "the reference implementation" other harnesses should be
built to. The residual risk this task closes is narrower but real: `Inhabited
HardwareExecutionResult` fabricates `faulted := false` as a default (reachable via `.getD`),
directly contradicting the harness's own "no fabricating path" docstring; and `getU8` returns `0`
for out-of-range reads, meaning an untouched, all-zero result buffer decodes as a plausible
(wrong) result — TCB notes only the positive control currently catches this class of bug.

TCB's proposed fix, and the reason this is genuinely interesting rather than pure cleanup:
**self-hosting**. Rebuild the harness's prologue/capture/epilogue machine code from
`X86_64Instruction.encode`, going through the same instruction registry TC4 built (the
`roundtripCases`-driven registry gate) — rather than 94 hand-transcribed byte literals. TCB: "the
hand-vs-generated diff is itself the one-time control vector" — running the self-hosting rebuild
once and diffing its output against the current hand-written bytes is a free, one-time
differential check that the harness has been byte-correct all along (or catches a divergence if
it hasn't been). This is why the task depends on TC4: the registry and its `encode` machinery are
the thing this task consumes.

## Deliverables & acceptance criteria

- `HardwareHarness.lean`'s prologue/capture/epilogue machine code rebuilt using
  `X86_64Instruction.encode` via the registry (TC4's roundtrip-gated instruction set), replacing
  the 94 raw `ByteArray.mk` literals.
- The hand-written-vs-generated byte diff run once and its result (identical, or the specific
  divergence found) reported in the completion report — this is a required one-time control
  vector, not optional verification.
- `setupSize` derived mechanically from the generated encoding's actual length rather than
  asserted as a manual constant.
- The `Inhabited HardwareExecutionResult` fabricator deleted (or its `faulted := false` default
  replaced with something that cannot silently stand in for a real result — e.g. a type that has
  no default, forcing every call site to handle absence explicitly).
- `getU8`'s out-of-range-returns-zero behavior addressed at the call sites that currently rely on
  the positive control alone to catch an untouched buffer — either bounds-check explicitly or add
  a sentinel/poison-fill so an unwritten result buffer cannot decode as a plausible-looking zeroed
  result.
- All existing hardware-fuzzer control vectors (positive: `mov rax, 0xC0FFEE1234`; negative: `div
  rbx` with `RBX=0`) still pass unchanged post-refactor — this task must not regress the harness
  it's improving.
- Completion report: the self-hosting diff result, confirmation the fabricator and out-of-range
  read hazards are closed, and the full existing fuzzer suite's pass count unchanged (e.g. the
  "59/59, 4939 vectors bit-exact" figure PLAN.md records for the current state, or whatever the
  current count is at time of work — reconfirm by running, don't assume PLAN.md's number is still
  current).
