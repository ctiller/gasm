# TC8: Trust⇒fuzzer buildout — one validation harness per TCB item

## Context

D13 (PLAN.md Decisions, ratified 2026-08-27) states the policy this task exists to make
concrete: **"everything trusted-but-unprovable (environment, hardware, APIs, tools) gets a
differential fuzzer validating our model of it."** TCB.md is the completed ledger (see TC7)
that names exactly what those things are; this task is where each ledger item that needs a
fuzzer (as opposed to a proof — see below) actually gets one built. TASKS.md's one-liner
scopes this concretely: **"one validation harness per TCB item (emitter/loader differential,
references-pipeline verification, oracle pinning, harness self-host) — after: TC7 (+ per-item
design docs, Law 5)."**

### Why this is genuinely Law-5-class, item by item

TASKS.md is explicit that this task needs **per-item design docs**, not one blanket design —
each TCB item names a different kind of "differential" (a PE parser diffing against
`dumpbin`/`pefile`; a Wasm module validator diffing against `wasm-tools validate`; a reference-
corpus hash manifest; an oracle-version pin-and-record mechanism), and Law 5 (`docs/REVIEW.md`)
requires the missing specification be authored and reviewed before the implementing code is
written, for each concept that isn't already fully designed in the repository. Do not treat
this as one big implementation task — it decomposes into as many design-then-implement cycles
as there are TCB items still needing a harness after TC7's decomposition.

### TCB's own preference order: proof beats fuzzer where shrinkable

Before building a fuzzer for any given item, check TCB.md's disposition for it. TCB.md's closing
section states the operating rule directly: **"Shrinkable... T5 and T10 are genuine
self-hosting opportunities — proof, not fuzzer: strictly better under Law 13's preference
order."** Concretely:

- **T5 (the emitter last mile, TCB's #1-ranked item)** — already has its own dedicated task,
  `TC14-emitter-connection-theorem.md`, which is explicitly proof-first (a PE parser + a
  `parse ∘ emit = id`-shaped connection theorem), with a structural differential against
  `dumpbin`/`pefile` as the *secondary* validation layer, not the primary one. Do not duplicate
  TC14's scope under TC8 — TC8's job for T5 is to ensure the differential-harness half (item 2
  of TC14's three-part fix: "structural differential vs dumpbin/pefile on every emitted binary")
  actually gets built as a fuzzer-shaped artifact with Law 13(4) control vectors (a corrupted-
  header negative control), complementing TC14's proof.
- **T10 (HardwareHarness's hand-written machine code)** — has its own dedicated task
  (`TC19-harness-self-hosting.md`); TCB's proposed fix there is self-hosting (rebuild the
  harness's prologue/capture/epilogue via `X86_64Instruction.encode` through the registry
  itself, per D11's DSL thesis) rather than a fuzzer diffing hand-written bytes against
  generated bytes forever. TC8's job for T10, if anything remains after TC19, is any residual
  differential-fuzzer-shaped validation TC19's self-hosting doesn't itself absorb.
- **T7 (Wasm binary emission)** — has its own dedicated task (`TC20-wasm-emission-roundtrip.md`)
  covering the missing LEB128 decoder and its roundtrip proof; the `wasm-tools validate` /
  `WebAssembly.validate` differential over every emitted spike module (with a byte-flip negative
  control) is the fuzzer-shaped half TC8 should ensure lands.
- **T8 (references pipeline)** — has its own dedicated task, `docs/tasks/TC16-references-
  integrity.md`; this is the "references-pipeline verification" TASKS.md's one-liner names
  explicitly. TCB's proposed fix (a per-file SHA-256 manifest, `--verify` failing nonzero on
  mismatch, commit-SHA pinning) is itself closer to a build-failing check than a differential
  fuzzer in the oracle-vs-model sense — confirm with TC16's own file whether it needs anything
  further from TC8.
- **T9 (oracle environment unpinned)** and **T4 (gate tooling exists, nothing runs it)** are
  already folded into TC5 (the gate runner), per TC5's own "TCB ledger items this task closes"
  section — TC8 should not duplicate that work, only confirm it landed.
- **T6 (IAT/loader convention)** — TCB's proposed fix is a genuine differential harness: "Win32
  differential harness dumps the real post-load IAT and diffs vs synthesized; re-key
  interception on resolved VA." This is squarely N1/N2's territory (the Win32 API differential
  harness design and its implementation), which TCB.md itself cross-references. TC8's role here
  is to confirm the IAT-specific differential gets built as part of N1/N2's scope, or to build
  it directly if N1/N2 doesn't cover it.
- **T3 (elaboration-time metaprograms)**, **T12 (verification harness layer)**, and **T13 (git/
  build-cache/result persistence)** are the remaining ledger items TCB.md marks "shrinkable" but
  that do not yet have a named dedicated task at time of writing — these are TC8's most direct
  scope: read each T-item's "Fix:" line in TCB.md, author a short per-item design note (inline
  design is likely appropriate for these — they read as mechanical: fold a filesystem-vs-closure
  check into T2's harness (T3); change a trace type to `Except Exhausted (List Event)` and delete
  dead code (T12); add a clean-tree build step to the merge-train sign-off process (T13)), and
  implement.

### The "harness self-host" phrase in TASKS.md's one-liner

TASKS.md's parenthetical ("emitter/loader differential, references-pipeline verification,
oracle pinning, harness self-host") is a compressed pointer to exactly the four items enumerated
above (T5/T14, T8, T9/T5-gate-runner, T10/T19) — read it as a summary of where TC8's four
biggest sub-threads live, not as four separate new things to build from scratch under this task
alone.

## Deliverables & acceptance criteria

- For every TCB.md item not already fully covered by TC5, TC14-TC20, or N1/N2: a per-item design
  note (inline `## Design` section in that item's own task file for mechanical items; a real
  `docs/` design doc, reviewed before implementation, for anything Law-5-class per the
  discussion above) followed by an implementation.
- Every fuzzer/differential harness built under this task must carry Law 13(4)'s mandatory
  positive-and-negative control vectors before any of its results count — this project has
  already been burned twice (TC1, TC2) by harnesses that silently fail-open when their
  external dependency is absent; do not repeat that class here. State explicitly, per harness,
  what the positive control is (a known-good artifact/case that must pass) and what the negative
  control is (a known-bad one that must be rejected), and demonstrate both in the completion
  report.
- Where TCB.md itself states a preference for proof over fuzzer (T5, T10), confirm the proof-
  shaped task (TC14, TC19) is the primary vehicle and scope this task's contribution as the
  complementary differential layer only, not a competing implementation.
- A completion report that walks TCB.md's T1-T13 list explicitly, stating for each: which task
  covers it, whether that coverage is proof-first or fuzzer-first, and what evidence (control-
  vector pass/fail, or theorem compiling clean) demonstrates it is actually closed — not just
  claimed closed.
