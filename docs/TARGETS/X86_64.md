# Target Specification: x86-64

This document defines the machine state model, instruction encodings, and semantics for the 64-bit x86 architecture (**x86-64 / AMD64 / Intel 64**).

---

## 1. Machine State Model & Sub-Register Aliasing

### 1.1 General Purpose Registers (GPRs) & 32-Bit Zero-Extension
16 64-bit general-purpose registers with aliased sub-registers:

| 64-bit | 32-bit | 16-bit | 8-bit Low | 8-bit High | Description |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `RAX` | `EAX` | `AX` | `AL` | `AH` | Accumulator |
| `RCX` | `ECX` | `CX` | `CL` | `CH` | Counter (shifts/loops) |
| `RDX` | `EDX` | `DX` | `DL` | `DH` | Data register |
| `RBX` | `EBX` | `BX` | `BL` | `BH` | Base register |
| `RSP` | `ESP` | `SP` | `SPL` | — | Stack pointer |
| `RBP` | `EBP` | `BP` | `BPL` | — | Base / Frame pointer |
| `RSI` | `ESI` | `SI` | `SIL` | — | Source index |
| `RDI` | `EDI` | `DI` | `DIL` | — | Destination index |
| `R8`–`R15` | `R8D`–`R15D` | `R8W`–`R15W` | `R8B`–`R15B` | — | Extended GPRs |

### Hardware Zero-Extension Invariant
On x86-64 hardware:
- Writing to a **32-bit sub-register** (`EAX`, `EBX`, `ECX`) **automatically zero-extends into the upper 32 bits** of the 64-bit register (`RAX`, `RBX`, `RCX`).
- Writing to an **8-bit or 16-bit sub-register** leaves the high bits of the register untouched.

```lean
/-- 32-bit register write clears upper 32 bits -/
def setReg32 (r : Register x86_64 .w64) (val : BitVec 32) (m : MachineState x86_64) : MachineState x86_64 :=
  m.setReg64 r (val.zeroExtend 64)
```

## 2. Binary Instruction Encoding

An x86-64 instruction consists of up to 15 bytes formatted as follows:

```
+-------------------+------------+---------+--------+-----+--------------+-----------+
| Legacy Prefixes   | REX Prefix | Opcode  | ModR/M | SIB | Displacement | Immediate |
| (0-4 bytes)       | (0-1 byte) | (1-3 B) | (0-1B) |(0-1)| (0,1,2,4,8 B)| (0,1,2,4B)|
+-------------------+------------+---------+--------+-----+--------------+-----------+
```

## 3. Memory Model & Ordering Proofs: x86 TSO vs Weak Ordering

Hardware x86-64 enforces **Total Store Order (TSO)** on standard Write-Back cacheable memory:
1. **Load-Load Ordering**: Loads are never reordered with other loads ($L \to L$ preserved).
2. **Store-Store Ordering**: Stores are never reordered with other stores ($S \to S$ preserved).
3. **Load-Store Ordering**: Loads are never reordered with subsequent stores ($L \to S$ preserved).
4. **Store-Load Exception**: A store followed by a load to a *different* address may be reordered ($S \to L$ may reorder).

### 3.1 Cacheability Preconditions & Non-Temporal Store Exceptions
The automatic release/acquire property on plain `MOV` instructions is strictly valid for **Write-Back (`WB`) cacheable memory**. 

- **Streaming Stores (`MOVNTI`, `MOVNTDQ`)**: Non-temporal stores bypass cache hierarchy and allow $S \to S$ reordering; they require `SFENCE`.
- **Write-Combining (WC) & MMIO**: Memory-mapped I/O registers and framebuffer memory permit store reordering; they require explicit `SFENCE` / `MFENCE` serializations.

```lean
theorem x86_mov_store_is_release (m : MachineState x86_64) (addr : Addr) (val : BitVec 64) :
  m.getMemoryType addr = .WriteBack →
  m.isNonTemporalInstr = false →
  PreservesStoreStoreOrder ∧ PreservesLoadStoreOrder
```

### 3.2 Stack Alignment Invariant
- **Function Entry**: $RSP \equiv 8 \pmod{16}$ (due to pushed return address).
- **Call Site**: $RSP \equiv 0 \pmod{16}$ (must be 16-byte aligned before `CALL`).

## Encodable Instruction Registry & Roundtrip Gate

Historically, `Decoder.lean` was extended by hand each time a new instruction was encoded, and it
repeatedly fell behind: encoders for `CALL rel32`, the `0x81 /0 /5 /7` immediate cluster,
`SHL/SHR r64, CL`, `MOVZX`, and the LEA `mod=2` form all shipped with no decoder counterpart, and
`0x8B` silently misdecoded a 32-bit `REX.W=0` load as a 64-bit one. Each gap was only found by an
adversarial review reading both sides by hand. This section makes that class of bug a **build
failure** instead of a review finding, via three stacked forcing functions.

### 1. The `roundtripCases` typeclass field

`X86_64Instruction.roundtripCases : List ι` (declared in `Instructions/Base.lean`) has **no
default**. Every `instance : X86_64Instruction Foo` — all ~78 of them — must supply a finite,
representative sample of `Foo`'s constructor argument domain, or the file does not compile. This
turns "did anyone remember to test this instruction's roundtrip" from a review question into a
compile error.

**This is a curated, representative sample, not an exhaustive enumeration of every argument
combination** — it is deliberately linear-in-domain-size, not a full cross product, so the
aggregate registry stays in the low thousands and the gate builds fast. It is exhaustive only over
the finite list each instance actually declares (`roundtripCases`), not over the full space of
`(register × immediate × REX-bit)` combinations a real disassembler could see. Concretely:
- A single `Reg64`/`Reg32` argument: the full 16-register list (`allReg64List` / `allReg32List`
  in `Instructions/Base.lean`).
- Two register arguments (dst, src): each of the 16 registers paired against a fixed anchor
  (`.rax`) in the *other* slot, once per slot — i.e. `(r, .rax)` for all `r`, plus `(.rax, r)` for
  all `r` — **plus** a fixed set of three both-extended pairs, `extendedReg64Pairs` /
  `extendedReg32Pairs` = `[(.r8,.r15), (.r12,.r13), (.r15,.r8)]` (register-width analog). The
  anchor-only convention alone never sets REX.R *and* REX.B simultaneously (the anchor slot is
  always the non-extended `.rax`), which an adversarial mutation exploited: a bug conditioned on
  *both* operands being extended (`makeRex true srcExt false (dstExt && !srcExt)`) passed every
  gate and `test_roundtrip` cleanly. The three explicit pairs close that specific hole; they do
  **not** cover the full 256-pair product, only that these three representative both-extended
  combinations decode correctly.
- A register plus an immediate/displacement: the full register list against the immediate list's
  first (zero) element, the full curated immediate list against the `.rax` anchor, **and** the full
  curated immediate list again against one extended anchor register (`.r15` / `.r15d`) — so every
  boundary immediate is exercised against at least one extended register, not only against `.rax`.
- A fixed-register form (e.g. `ADD RSP, imm`) with only an immediate field: the curated immediate
  list alone (no register to vary).
- Base+displacement memory forms (LEA, MOV/MOVZX through memory): the destination register list,
  the base register list, and the curated displacement list, each varied independently against
  `.rax`/zero anchors for the others, plus the same both-extended-pair and boundary-immediate/
  displacement-against-`.r15` additions as above for any register slot(s) present.
- No-argument instructions (`RET`): a single case.

Curated immediate/displacement values are zero, a representative small magnitude, and the
type's signed/unsigned boundary values (`0x7F`/`0x80`/`0xFF` for `UInt8`; `0x7FFFFFFF` /
`0x80000000` / `0xFFFFFFFF` for `UInt32`; `±0x1000` and `INT32_MAX`/`INT32_MIN` for `Int32`).

**What this convention still does not cover** (known, accepted gaps, not silently assumed away):
the full register × register × immediate cross product for any three-or-more-argument family; REX
prefix combinations beyond "neither extended" / "exactly one extended" / the three named
both-extended pairs (e.g. it does not independently vary REX.X, which no encoder in this codebase
sets); and boundary immediates crossed against every register rather than one extended anchor.
Closing one of these classes of hole is exactly how the both-extended gap above was found in the
first place, so this list should be read as "known open questions", not "impossible in principle".

### 2. The registry and the environment audit

`Gasm/Targets/X86_64/Registry.lean` defines `allEncodableInstructions : List AnyX86_64Instruction`,
the concatenation of every family's `roundtripCases` (each lifted into the open existential
`AnyX86_64Instruction` wrapper via `⟨_⟩`), sourced transitively through the `RoundtripGate/*.lean`
shards (see below).

Enumerating `roundtripCases` by hand in a manifest, however, is exactly the kind of list that
silently drifts (this is precisely how `allSupportedInstructionSuite` in `SemanticsFuzzer.lean`
had already gone stale relative to the decoder before this change). So `Registry.lean` additionally
runs a `run_cmd` elaboration-time audit: it walks `Lean.Meta.instanceExtension.getState env` (every
registered typeclass instance in the whole environment, keyed by declaration name, each carrying
its instantiated type via `entry.val`'s inferred type), filters for instances whose inferred type
has head constant `X86_64Instruction`, and extracts the concrete argument type name from each. That
live set is compared, as plain `List Name` equality, against a hand-maintained
`expectedInstructionTypes : List Name` manifest in the same file. Any mismatch — a new
`instance : X86_64Instruction Foo` that forgot to register `Foo` in the manifest (and, by
construction, forgot to add a `RoundtripGate` case for it), or a stale manifest entry whose
instance was deleted — makes `Registry.lean` fail to elaborate with a message naming the exact
symmetric difference. This is the "acceptable fallback" audit design (a hand-maintained name list
compared against the live environment) rather than a bespoke `@[x86_instr]` attribute, chosen
because it needs no custom attribute infrastructure and the API used
(`Lean.Meta.instanceExtension`) is stable, ordinary Lean 4 metaprogramming.

### 3. The gate theorem(s) — sharded by family

Rather than one monolithic `native_decide` over the full ~78-instruction registry (which would
serialize all obligations behind one large kernel/compiler call and name only "the registry" on
failure), the gate is **sharded one file per instruction family** under
`Gasm/Targets/X86_64/RoundtripGate/` (`Add.lean`, `Sub.lean`, `Mov.lean`, `Jcc.lean`, ... — one per
existing `Instructions/*.lean` file, the same grouping the codebase already uses). Each shard:
1. Builds its own family's `List AnyX86_64Instruction` from the family's `roundtripCases` fields.
2. Proves `theorem <family>_roundtripGate : (<family>Cases).all decodesOk = true`.

`decodesOk` (`RoundtripGate/Common.lean`) is the equality relation for the gate. `DecodesTo`
(`Roundtrip.lean`) is defined as `decodeX86_64Instr (encode i) 0 = Except.ok (i, (encode i).size)`,
which needs `DecidableEq`/definitional equality on the *decoded* instruction against the *original*
`i : AnyX86_64Instruction` — fine for `rfl` on a single concrete ground instance, but
`AnyX86_64Instruction` (an open existential over a hidden type `α`) has no general `DecidableEq`
instance to drive a `List.all` over a mixed-family list. So `decodesOk` instead uses the
byte/length/rendering conjunction this doc's task explicitly sanctions: (a) decoding succeeds, (b)
the decoded length equals the encoded byte count, (c) re-encoding the decoded instruction reproduces
the original bytes exactly, and (d) `toLean` renderings of the decoded and original instructions
match (guards against a same-bytes-different-structure misdecode, e.g. the `0x8B` REX.W bug this
change fixed, where the bytes for a 32-bit RSP load and a 64-bit one can coincide for other
opcodes/forms). Every shard is discharged by plain `decide` (kernel-checked, not compiler-trusted)
— no shard has needed `native_decide`. Two shards (`Mov`, `Cmov`) exceed the kernel's default
reduction-stack depth on their larger case lists and raise `maxRecDepth` (to 4000) as a tactic-local
`set_option ... in decide`, which is still `decide`, just given more stack; this is noted in each
shard's own doc comment rather than claimed generically here. Each gate is an exhaustive,
kernel-checked pass over its family's *declared* `roundtripCases` list — see the "what this
convention still does not cover" note in section 1 above for what that list does and does not
include; it is not a claim of exhaustiveness over every value of every argument type.

`Gasm/Targets/X86_64/RoundtripGate.lean` is a thin aggregator that imports every shard, so building
it (transitively, building `Gasm`) forces every family's gate theorem to elaborate.

**Known intermittent risk — parallel elaboration memory pressure.** One clean `lake build Gasm` in
two, run under this same 21-shard gate, hit `std::bad_alloc` while elaborating the `Xchg` shard —
a small shard with no `maxRecDepth` bump of its own, so the failure is collateral pressure from all
21 shards' `decide` calls (including the two `maxRecDepth 4000` ones) running concurrently, not a
defect in `Xchg` itself. `MovR64Imm64.roundtripCases` (the single largest list, crossing 16
registers and a 17-element curated `UInt64` value list twice) was trimmed to a 5-element
boundary-only `curatedUInt64Cases`, cutting the MOV family from 372 to 348 cases — a real but
modest reduction; it narrows one contributor to peak memory, it does not deterministically prevent
the failure, since the underlying cause is aggregate concurrent memory pressure across many OS
processes, not any single shard's size. A build that hits this should simply be re-run (the gate
is deterministic; nothing here is flaky in the sense of "sometimes reports a false pass") — but an
intermittently-OOMing gate is a bad experience, and a real fix (capping parallelism for this
target specifically, or restructuring so `decide` runs against smaller batches per process) is
future work, not attempted here.

### 3b. REX.B on SIB-base-4: derive it, or reject rather than misdecode

Four decoder sites read a ModRM/SIB pattern where the SIB base field is 4 (the "no base register
in ModRM, use SIB.base instead" escape) with SIB.base itself also 4 — the pattern that means "RSP"
when REX.B is unset and "R12" when REX.B is set: `0x8B` (MOV load), `0xC7` (MOV store imm32), `0x8D`
(LEA), and `0xC6` (MOV store imm8). All four originally ignored REX.B and always decoded this
pattern as RSP; `0x8B` and `0xC7` were fixed to derive the base register via `codeToReg64 4 rexB`
(the same idiom every other SIB path in this decoder already uses) because this codebase has a
general structure — `MovReg64Mem64Disp`, `MovMem64DispImm32` — that can represent an R12 base.
`0x8D` (LEA) and `0xC6` (MOV byte imm8) have no such structure: `LeaRspDisp`/`LeaRspDisp32`/
`MovRspDispByte` are hardcoded to RSP with no base-register field at all, so there is nothing to
decode an R12-based encoding *into*. Rather than silently decoding those bytes as an RSP form
anyway (which is exactly the misdecode class this whole gate exists to prevent), the decoder
rejects them outright (`.error "Unsupported base register (R12 via REX.B) ..."`). This is not
encoder-reachable today (nothing in this codebase emits `lea reg, [r12+disp]` or
`mov byte [r12+disp], imm8`), but `disassembleX86_64` is a public entry point over arbitrary bytes,
so a correct disassembler must not claim a wrong answer for a byte pattern with no correct
representation, even one no encoder here produces.

### 4. Derived suites

`RoundtripTests.lean`'s exhaustive IO executable now iterates `allEncodableInstructions` (kept for
human-readable diagnostics — `[FAIL]` lines naming the exact NASM mnemonic and byte mismatch — the
gate theorems are the actual correctness proof, not this IO loop). `SemanticsFuzzer.lean`'s
`allSupportedInstructionSuite` is likewise derived as `allEncodableInstructions.filter
canFuzzHardware` instead of a hand-maintained literal list, closing the exact drift class the
adversarial review found (hand-lists silently omitting instructions the decoder already disagreed
with).

### 5. Stage B decoder modularization

**Implemented** (B3, after TC4 and B1 landed, protected by TC4's registry gate throughout). This
section originally sketched Stage B as design-only; it now describes what was actually built, and
notes drift from the original sketch.

The registry/gate in §4 was originally layered on top of a monolithic `Decoder.lean`: editing any
one instruction's decode branch invalidated the whole `Decoder.lean` module (a single 700+-line
`decodeX86_64Instr` pattern match owning every family's byte-level decode logic), which
re-elaborated every `RoundtripGate/<Family>.lean` shard that transitively depended on it. Stage B
removes that coupling in two parts:

- **Per-instruction `tryDecode` co-located with `encode`.** Every `Instructions/<Family>.lean` file
  now owns a `<family>TryDecode : ByteArray → Nat → Except String (AnyX86_64Instruction × Nat)`
  function next to that family's `encode` helpers — the same REX/ModR/M-parsing and per-opcode
  logic `Decoder.lean` used to own centrally, moved next to the family it decodes. Each
  `tryDecode` claims only its own family's byte patterns and returns `.error` for anything else
  (verified exhaustively per family, see below). Shared REX/ModR/M-parsing boilerplate
  (`parseRexAndOpcode`, `readModRM`) lives in `Instructions/Base.lean`, which every family already
  imported.
- **Local roundtrip proof, generalized over the decoder.** `RoundtripGate/Common.lean`'s
  `decodesOk` predicate is now parameterized by *which* decoder function to check
  (`decodesOk (tryDecode : ByteArray → Nat → Except String (AnyX86_64Instruction × Nat))`) instead
  of hard-coding the global `decodeX86_64Instr`, and no longer imports `Decoder.lean` at all. Each
  `RoundtripGate/<Family>.lean` shard instantiates it with that family's own `tryDecode`
  (`<family>FamilyCases.all (decodesOk <family>TryDecode) = true`), so a shard's roundtrip proof
  now depends only on its own family's `Instructions/<Family>.lean` file plus `Common.lean` — not
  on `Decoder.lean`, and not on any other family.
- **`Decoder.lean` reduced to a thin dispatcher.** `decodeX86_64Instr` is now `tryDecoders
  allTryDecoders bytes offset`: `allTryDecoders` lists every family's `tryDecode` (25 entries, one
  per family) and `tryDecoders` tries each in order, returning the first success. All opcode
  knowledge lives in the per-family functions; the dispatcher itself inspects no bytes. This *is*
  the "registry-driven dispatcher" the original sketch called for, though it is a plain ordered
  `List` of functions defined in `Decoder.lean` rather than a reuse of `Registry.lean`'s
  `allEncodableInstructions` — that registry is a list of proof witnesses (`AnyX86_64Instruction`
  values for the roundtrip gate), not decoder functions, so there was nothing there to reuse
  directly; investigated and noted as drift from the original "reusing that registry machinery"
  phrasing, not an oversight.
- **Dispatch-reachability and in-bucket exclusivity**, the two new proof obligations Stage B's
  design called for:
  - *In-bucket exclusivity* (no two of one family's own byte patterns collide ambiguously) is
    proved generically once, as `RoundtripGate.inBucketExclusiveOf` in `Common.lean` — a corollary
    of a family's own `decodesOk`-based roundtrip gate (if every witness in a family's
    `roundtripCases` decodes correctly, two witnesses that encode to identical bytes must render
    identically), not a fresh `decide` obligation over `O(n²)` pairs. Every
    `RoundtripGate/<Family>.lean` shard instantiates it as `<family>Family_inBucketExclusive`.
  - *Dispatch-reachability* (does the dispatcher route every registered instruction to its own
    family's `tryDecode`, i.e. does no earlier entry in `allTryDecoders` shadow it?) is proved per
    family in a new module, `RoundtripGate/DispatchExhaustive.lean`, as
    `<family>Family_dispatchReachable : <family>FamilyCases.all (decodesOk decodeX86_64Instr) =
    true` — the same `decodesOk` predicate every shard already uses, instantiated with the real
    dispatcher instead of the family's own `tryDecode`. This is the one module the B1 review
    (see `docs/tasks/B3-stage-b-decoder-modularization.md`'s "design constraint from the B1
    review" note) explicitly allows full fan-in: it imports `Decoder.lean` (which imports every
    family, since the dispatcher must be able to route to any of them) and every
    `RoundtripGate/<Family>.lean` shard.

**Drift from the original sketch: `DispatchExhaustive.lean` is deliberately *not* wired into the
default `Gasm` build.** The original sketch's "editing one instruction rebuilds only that file, the
thin dispatcher, and one composition lemma" implied the reachability lemma would sit in the normal
build path. Measured, it cannot without giving back most of Stage B's win: exhaustively
kernel-checking the real dispatcher against all ~1611 registered witnesses (a 25-way `decide`
try-chain per witness, in the worst case) costs roughly 100s of wall time by itself — wiring it into
the `RoundtripGate` aggregator (which `Registry.lean`, and so `Gasm`, imports) turned a single-family
edit's cascade from 14 modules / ~30s into 15 modules / ~177s, *worse* than the pre-Stage-B baseline
of 39 modules / ~130s on the metric (wall time) that actually matters for edit-loop latency. Given
that trade, `RoundtripGate.lean`'s aggregator does not import `DispatchExhaustive.lean`; the module
still compiles as a complete, zero-`sorry`, zero-new-axiom proof, reachable directly via `lake build
Gasm.Targets.X86_64.RoundtripGate.DispatchExhaustive` (recommended as an explicit CI step, not yet
wired as one), so the obligation is proved and available without taxing every local edit-test cycle.

Net effect, matching the original sketch's build-perf claim (the "one composition lemma" clause
aside, per the drift note above): editing one instruction's file now rebuilds only that file, the
thin dispatcher (`Decoder.lean`, since it imports every family to route — expected, not a residual
defect), and a small number of structurally-required downstream consumers (`Instructions.lean`'s
umbrella manifest, `Registry.lean`, `Assembler.lean`/`Disassembler.lean`/`Roundtrip.lean`,
`SemanticsFuzzer.lean`) — not the other 24 families' `RoundtripGate/<Family>.lean` shards, and not
`DispatchExhaustive.lean`. See `docs/tasks/B3-stage-b-decoder-modularization.md`'s Notes for the
measured before/after module-rebuild count and wall time for a single-instruction edit.
